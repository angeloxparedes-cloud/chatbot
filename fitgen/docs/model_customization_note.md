# Model Customization Note — PEFT/LoRA/QLoRA Rationale

**Checkpoint 4, Deliverable 15.**

## Decision: we use the base Gemini model as-is, without fine-tuning

FitGen calls Google's hosted `gemini-2.5-flash` through the Gemini
Developer API rather than fine-tuning an open-source model with
LoRA/QLoRA. This section justifies that decision and outlines what
fine-tuning *would* look like if we changed course.

## Why we did not fine-tune

1. **We don't control the weights of a hosted API model.** LoRA/QLoRA
   fine-tuning requires access to the base model's weights to attach
   low-rank adapters to (typically attention projection layers). Gemini,
   accessed via API, doesn't expose weights — fine-tuning it would require
   Google's managed tuning service (a different, separate workflow from
   PEFT), not local LoRA/QLoRA.
2. **RAG already solves our actual problem.** Our core requirement is
   *factual grounding* — answers must come from our exercise database and
   training-principle documents, not the model's general knowledge. RAG
   (retrieval + prompt injection) solves this directly, while fine-tuning
   solves a different problem: teaching a model new *behavior/style*
   patterns. Fine-tuning would not, by itself, stop hallucination the way
   retrieval grounding does — the model would still need a retrieval step
   unless we baked our entire ~85-chunk dataset directly into weights,
   which is both wasteful for a dataset this small and harder to update
   than just re-running the ingestion pipeline when we add exercises.
3. **Dataset size doesn't justify it.** LoRA/QLoRA fine-tuning shows the
   most benefit with either (a) a large, style-consistent dataset (hundreds
   to thousands of examples) or (b) a narrow, repetitive output format that
   benefits from being "baked in." Our ~52 exercises + 5 reference
   documents is exactly the right size for RAG and too small to usefully
   fine-tune a model without overfitting to our own phrasing.
4. **Cost/compute constraints.** As a budget-conscious student project
   (see Problem Statement — the whole premise of FitGen is an affordable
   alternative to a personal trainer), spinning up GPU compute for
   QLoRA fine-tuning of even a small open-source model (e.g., a Llama or
   Gemma variant) adds infrastructure cost and complexity disproportionate
   to the benefit, when Gemini's free API tier already meets our latency
   and quality targets from the Project Proposal's Success Criteria.

## If we *did* fine-tune: what we would target

Hypothetically, if FitGen moved to a self-hosted open-source base model
(e.g., `Gemma 2 9B` or `Llama 3.1 8B`) and wanted to apply QLoRA:

- **Target**: the *output formatting behavior*, not factual knowledge —
  training the model on examples of our exact desired workout-plan format
  (`**Day 1:** Exercise — sets x reps (rest)...`) so it reliably produces
  that structure with fewer explicit formatting instructions in the
  prompt, freeing up context-window budget for retrieved content instead.
- **Method**: QLoRA (4-bit quantized base weights + trainable low-rank
  adapters on the attention `q_proj`/`v_proj` matrices) to keep the
  fine-tuning run feasible on a single consumer GPU (e.g., a 16–24GB card),
  which matters given our "memory constraints" framing from the course.
- **Data**: 100–300 synthetic (question, ideal-formatted-answer) pairs
  generated by prompting a strong model (e.g., Gemini) against our own
  retrieved contexts, then lightly hand-reviewed for correctness — this
  keeps the fine-tuning data grounded in the same source-of-truth documents
  the RAG system already uses, rather than introducing new "knowledge"
  through weights.
- **What we would NOT try to bake in via fine-tuning**: the actual exercise
  facts (muscle groups, equipment, safety notes). Those should keep coming
  from retrieval so the source-of-truth dataset can be updated (e.g., add
  new exercises) without needing to re-run a fine-tuning job every time.

## Summary
RAG (retrieval-augmented, hosted Gemini) is the right architecture for
*this* project's actual constraint (accurate, sourceable fitness
information), and fine-tuning would be solving a problem we don't
currently have. We'd revisit this if a future iteration needed the model
to reliably produce a much more complex structured output (e.g., JSON for
a downstream app) at high volume, where LoRA-tuned formatting could reduce
prompt-engineering overhead and token cost per request.
